# Практическая работа № 2. Модульное тестирование

**Время: 90 минут. Язык: C#. Инструмент: MSTest. Работа индивидуальная.**

Вы получили модуль расчёта стоимости заказа. Он запускается, но может нарушать требования. Ваша задача — проверить его автоматическими модульными тестами и доказать найденные нарушения. Исправлять модуль не нужно.

## Что должно получиться

К концу пары в вашем репозитории: исходный проект без изменений, минимум 12 тестовых случаев (включая пример), заполненный `REPORT.md` и результат запуска в формате TRX. Строки параметризованного теста считаются отдельными случаями. Повтор одинаковой проверки с другими случайными числами сам по себе не повышает оценку.

**Зелёными должны стать не все тесты.** Корректный тест, обнаруживший нарушение требований, должен падать. Не подгоняйте ожидания под реализацию. Набор только из падающих тестов тоже недостаточен: нужны проверки корректно работающих сценариев.

## 1. Контракт модуля

```csharp
PriceCalculator.CalculateTotal(decimal subtotal, bool loyalty, bool express)
```

- `subtotal` — стоимость товаров до скидок, в рублях; тип `decimal`.
- `loyalty` — есть ли карта постоянного покупателя.
- `express` — выбрана ли экспресс-доставка.
- результат — итоговая стоимость товаров и доставки, в рублях.

Требования являются источником ожидаемых результатов. Исходный код — проверяемая реализация.

| ID | Требование |
| --- | --- |
| R1 | Допустимая стоимость товаров — от 0 до 100 000 рублей включительно. Вне диапазона метод выбрасывает `ArgumentOutOfRangeException`. |
| R2 | При стоимости товаров от 5 000 рублей включительно предоставляется скидка 5%. Ниже порога скидки по сумме нет. |
| R3 | Карта постоянного покупателя даёт скидку 10% независимо от суммы. Если подходят две скидки, применяется только большая. Скидки не складываются. |
| R4 | Обычная доставка стоит 300 рублей. При исходной стоимости товаров от 4 000 рублей включительно обычная доставка бесплатна. Порог определяется до скидки. |
| R5 | Экспресс-доставка всегда стоит 500 рублей, независимо от суммы заказа и карты. Она заменяет обычную доставку. |
| R6 | Сначала выбирается скидка. Стоимость товаров после скидки округляется до двух знаков: `MidpointRounding.AwayFromZero`. Затем прибавляется доставка. Скидка на доставку не действует. |

Для нулевой суммы применяются те же правила: доставка не отменяется. Входные значения с дробной частью допустимы. Налоги, промокоды, база данных и сетевые обращения в задачу не входят.

Пример: товары на 1 000 рублей, без карты, обычная доставка: `1000 + 300 = 1300`.

## 2. Подготовка и первый запуск — 0–10 минут

Нужен **.NET 8 SDK** и доступ к NuGet при первом восстановлении зависимостей. Установку и проверку доступа преподаватель организует до занятия. Проверьте SDK:

```bash
dotnet --list-sdks
```

В терминале перейдите в папку, где лежит этот README, и выполните:

```bash
dotnet restore tests/OrderPricing.Tests/OrderPricing.Tests.csproj
dotnet test tests/OrderPricing.Tests/OrderPricing.Tests.csproj
```

В стартовом проекте ровно один демонстрационный тест: он должен пройти. Это проверка работоспособности окружения, а не доказательство корректности модуля.

В Visual Studio можно открыть `tests/OrderPricing.Tests/OrderPricing.Tests.csproj`, собрать проект и запустить тесты через обозреватель тестов. Если среда предлагает установить SDK или восстановление NuGet не работает — сообщите преподавателю; не тратьте пару на установку.

## 3. Спроектируйте проверки — 10–25 минут

В `REPORT.md` кратко запишите выбранные случаи: входные данные, ожидаемый результат, ID требования и причину выбора. Для расчётов можно использовать калькулятор; нельзя получать ожидаемое значение вызовом тестируемого метода.

В наборе должны быть:

- обычный сценарий без скидки и сценарий с картой;
- значения по обе стороны каждого порога скидки и бесплатной обычной доставки, включая сам порог;
- сочетание карты со скидкой по сумме;
- экспресс-доставка при разных суммах;
- допустимые границы суммы и значения за ними;
- хотя бы одна проверка округления с дробной суммой.

Один случай может закрывать несколько требований. Минимум 12 — нижняя граница; если ваш набор не проверяет перечисленные группы, добавьте случаи. Выбирайте данные так, чтобы было понятно, какое правило проверяется.

## 4. Напишите и запустите тесты — 25–60 минут

Добавляйте тесты в `tests/OrderPricing.Tests/PriceCalculatorTests.cs`. Название должно объяснять условие и ожидаемое поведение. В каждом тесте — подготовка, вызов метода и проверка результата. Каждый тест должен запускаться отдельно и не зависеть от предыдущих.

Числовые литералы для `decimal` пишутся с `m`, например `125.50m`. Не сравнивайте денежные результаты через `double`.

Проверка ожидаемого исключения в MSTest:

```csharp
Assert.ThrowsException<ArgumentOutOfRangeException>(() =>
    PriceCalculator.CalculateTotal(-1m, false, false));
```

В этом примере отсутствие исключения приводит к падению теста. Правильно выброшенное ожидаемое исключение означает, что тест прошёл.

По желанию используйте `[DataTestMethod]` и `[DataRow]`. У аргументов атрибутов C# есть ограничения: `decimal` нельзя передавать прямо в `[DataRow]`. Для этой работы достаточно отдельных `[TestMethod]`; параметризация не обязательна.

После падения проверьте последовательно: правильно ли прочитано требование, верно ли рассчитано ожидание, вызывается ли нужный метод, отличается ли фактический результат. Не перехватывайте все исключения и не используйте `Assert.IsTrue(true)`.

## 5. Зафиксируйте результат — 60–80 минут

Для каждого самостоятельного дефекта запишите один минимальный пример: ID требования, вход, ожидание, фактический результат и имя подтверждающего теста. Несколько падений из-за одного нарушенного правила — один дефект.

Искать точную строку ошибки в исходнике не требуется. Объяснения на уровне поведения достаточно. Количество заложенных дефектов заранее не сообщается.

Сохраните результат запуска:

```bash
dotnet test tests/OrderPricing.Tests/OrderPricing.Tests.csproj --logger "trx;LogFileName=unit-tests.trx" --results-directory evidence
```

Ненулевой код завершения при упавших проверках ожидаем. Ошибка компиляции, невозможность найти тесты или восстановить пакеты — это проблема запуска, а не найденный дефект расчёта.

## 6. Сдача и короткая защита — 80–90 минут

Разместите комплект в существующем репозитории, в разделе дисциплины «Тестирование», в папке `practice-02-unit-testing` (если преподаватель ранее задал точный путь — используйте его). Сдайте ссылку на папку или коммит.

Должны быть: `src/`, `tests/`, `README.md`, заполненный `REPORT.md`, `evidence/unit-tests.trx`. Папки `bin/` и `obj/` не нужны.

На защите объясните один проходящий и один падающий тест: почему выбраны данные, откуда взялось ожидание и какое требование проверяется. По просьбе преподавателя измените входные данные и предскажите результат до запуска.

Справочники и ИИ допустимы как помощь с синтаксисом. Вы отвечаете за выбранные проверки и объяснение результата. Копирование готового набора без понимания не подтверждает выполнение работы.

## Как оценивается работа

- **4 балла:** обоснованный набор проверяет перечисленные группы требований, границы и сочетания условий.
- **3 балла:** тесты запускаются, содержат реальные утверждения, независимы; исключения проверяются как ожидаемые.
- **2 балла:** дефекты доказаны воспроизводимыми примерами; фактические результаты не перепутаны с ожидаемыми.
- **1 балл:** комплект воспроизводится по инструкции, отчёт заполнен, студент объясняет свои проверки.

Максимум — 10 баллов. Каждый пункт оценивается частично по выполненным условиям. Работа без запускаемых собственных тестов не подтверждает освоение темы и возвращается на доработку. Исправление исходного модуля не засчитывается вместо тестирования.

Справка по инструменту: [официальный вводный материал Microsoft по C# и MSTest](https://learn.microsoft.com/dotnet/core/testing/unit-testing-csharp-with-mstest).
